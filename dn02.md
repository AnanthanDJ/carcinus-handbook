# Design Note 02

# Public Key Cryptography and the Key Distribution Problem

> "Symmetric encryption solved one problem beautifully.
>
> It also created another."

---

# The Story So Far

In the previous design note we learned that symmetric encryption uses one shared secret key.

Alice encrypts a message.

Bob decrypts the message.

```
Alice
  │
  │  Secret Key
  ▼
Encrypted Data
  ▼
Bob
```

Algorithms like AES are incredibly fast.

Modern processors even contain hardware dedicated to accelerating AES.

So...

if AES is already secure,

why does RSA exist?

---

# The Key Distribution Problem

Imagine Alice wants to send Bob an encrypted message.

Alice needs a secret key.

Bob also needs the same secret key.

Question.

How does Alice send Bob the key?

She cannot simply send

```
Secret Key = 123456
```

because anyone intercepting that message now possesses the key.

The entire purpose of encryption is lost.

---

Imagine trying to mail someone a locked safe.

You lock it.

Now...

how do you send them the key?

Putting the key inside the safe obviously doesn't work.

Sending it separately isn't safe either.

This was one of the biggest unsolved problems in cryptography for decades.

It became known as

**The Key Distribution Problem.**

---

# The Obvious Solution Doesn't Work

Someone might suggest

> "Let's meet in person and exchange the key."

That works.

Until you have

10 users.

Then 100.

Then 10,000.

Then an entire country.

The Internet needed a way for complete strangers to establish secure communication without ever meeting.

That seemed impossible.

Until the 1970s.

---

# A Revolutionary Idea

Suppose locks behaved differently.

Imagine a magical lock.

Anyone could close it.

Only one person could open it.

Normal locks don't work this way.

But mathematically...

they can.

This became the foundation of

**Public Key Cryptography.**

---

# Two Keys Instead of One

Instead of one shared key,

every person now owns two keys.

```
Public Key

Private Key
```

The names are surprisingly literal.

The public key is meant to be shared.

The private key must never leave its owner.

---

Imagine Bob creates two keys.

```
Public Key

Private Key
```

He uploads the public key to his website.

Everyone on Earth can download it.

This is perfectly safe.

---

Now Alice wants to send Bob a secret message.

She encrypts it using Bob's

Public Key.

Once encrypted,

only Bob's

Private Key

can decrypt it.

Not Alice.

Not an attacker.

Not even the public key itself.

Only the matching private key.

---

The beautiful part is this.

The public key can be shared with everyone.

Yet it reveals essentially nothing useful about the private key.

That is what makes the entire system work.

---

# Why This Was Revolutionary

For the first time,

two strangers on opposite sides of the world could establish secure communication

without ever exchanging a secret beforehand.

That single idea made possible much of the modern Internet.

---

# Where Do We Use Public Key Cryptography?

Almost everywhere.

Examples include

HTTPS

SSH

VPNs

Digital Signatures

Software Updates

Git Commit Signing

Package Managers

Secure Email

Authentication Tokens

Cloud Infrastructure

Whenever two computers have never met before,

public key cryptography is usually involved.

---

# Wait...

Does HTTPS Encrypt Everything Using RSA?

Surprisingly...

No.

This is one of the biggest misconceptions.

RSA is actually too slow to encrypt large amounts of data.

Remember,

AES is incredibly fast.

RSA is comparatively expensive.

So modern protocols combine both.

---

# Hybrid Encryption

Instead of choosing one algorithm,

modern systems use both.

The process looks something like this.

```
Client

↓

Generate Random AES Key

↓

Encrypt AES Key Using RSA

↓

Send Encrypted AES Key

↓

Server Decrypts AES Key

↓

Both Sides Now Share AES Key

↓

Everything Else Uses AES
```

Notice something.

RSA only solves

the key distribution problem.

AES still performs almost all of the actual encryption.

This design gives us

the convenience of RSA

and

the speed of AES.

---

# TLS Handshake

When you visit

```
https://google.com
```

your browser does not immediately start encrypting data.

Instead,

the browser and server first perform a negotiation.

A simplified version looks like this.

```
Client

↓

Hello

↓

Server Certificate

↓

Verify Certificate

↓

Exchange Keys

↓

Generate Shared Secret

↓

Begin AES Encryption
```

This initial negotiation is called the

TLS Handshake.

It is one of the most important cryptographic protocols on the Internet.

---

# Where Do Certificates Fit?

Remember certificates from the previous design note.

Certificates exist because

anyone

can generate a public key.

Suppose an attacker creates

```
Fake Google Public Key
```

How would your browser know?

It wouldn't.

Certificates solve this.

A trusted Certificate Authority verifies ownership.

Your browser trusts certain Certificate Authorities.

When Google presents its certificate,

your browser verifies

- the certificate
- the signature
- the ownership
- the expiration date

Only then does communication continue.

---

# Public Keys Are Everywhere

Organizations possess enormous numbers of public/private key pairs.

Examples include

TLS Certificates

VPN Authentication

Signing Keys

Code Signing Certificates

Container Signing

Secure Boot

Cloud Authentication

Each of these eventually becomes

a cryptographic asset.

Carcinus aims to discover them.

# Engineering Discussion

Notice something interesting.

The SIH problem statement never says

> Find RSA.

It says

> Discover cryptographic artefacts.

That wording is deliberate.

An organization might not use RSA at all.

It might use

ECC

Ed25519

AES

TLS

Certificates

Hardware Security Modules

VPN Keys

The scanner should not care.

Its job is not to judge.

Its first responsibility is simply to answer

"What exists?"

Only later can another system evaluate whether those assets are safe.

Discovery comes before assessment.

---

# Why This Matters

Everything we have discussed so far still assumes something important.

The mathematics behind RSA is difficult to reverse.

Specifically,

given a public key,

recovering the private key should take an impossibly long time.

For decades,

that assumption held true.

The security of RSA depends on it.

But what happens if a new type of computer appears...

that solves this mathematical problem much faster?

That question changed the future of cryptography.

And eventually gave birth to

Post-Quantum Cryptography.

That is the story of our next design note.

---

# Things To Remember

• Symmetric encryption requires both parties to possess the same secret key.

• Securely sharing that key is called the Key Distribution Problem.

• Public Key Cryptography solves this problem using two keys.

• Public keys are shared.

• Private keys are never shared.

• RSA is mainly used to establish trust and exchange secrets.

• AES is usually responsible for encrypting the actual data.

• Modern protocols combine both approaches.

• Certificates prove ownership of public keys.

• Public keys, certificates and signing keys are all cryptographic assets.

• Discovery always comes before assessment.
