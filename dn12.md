```

↓

↓

Normalization

↓

CBOM

↓

↓
```

Every language expresses cryptography differently.

Java

↓

Rust

↓

Go

↓

Python

↓

Configuration Files

↓

Certificates

↓

Container Metadata

↓

Common IR

Output

```
Standardized cryptographic artifacts.
```

---

# Stage 3 — CBOM

The normalized artifacts are stored in the

Cryptographic Bill of Materials.

Think of it as

the organization's cryptographic inventory.

It answers questions like

```
Which repositories use RSA?

Which certificates expire soon?

Which libraries implement TLS?

Which applications still depend on SHA-1?
```

The CBOM becomes the single source of truth.

---

# Stage 4 — Risk Engine

The Risk Engine evaluates every artifact.

It considers

```
Algorithms

↓

Configurations

↓

Protocols

↓

Metadata

↓

Business Context
```

Output

```
Risk Findings
```

Example

```
High

Medium

Low

Critical
```

Along with

confidence,

evidence,

and explanations.

---

# Stage 5 — Recommendation Engine

The Recommendation Engine converts findings into actions.

Example

```
Finding

↓

RSA-1024

↓

Recommendation

↓

Plan migration toward standardized PQC-compatible deployment.

↓

Priority

High
```

Notice something.

The Recommendation Engine does not perform discovery.

It consumes findings.

# Why This Architecture Scales

Suppose tomorrow we support

```
Kotlin
```

What changes?

Only one component.

```
New Parser

↓

Normalization

↓

Existing IR
```

Everything else remains untouched.

Now suppose we add

```
Binary Analysis
```

Again,

only Discovery changes.

The Risk Engine,

Dashboard,

CBOM,

Recommendations,

all continue working.

This is the power of loose coupling.

# Where Go Fits

Go is responsible for orchestration.

Examples include

- repository scanning
- scheduling
- REST API
- backend services
- database access
- dashboard communication
- report generation

Go excels at building reliable backend services.

---

# Where Rust Fits

Rust is responsible for performance-critical components.

Examples include

- parsing
- normalization
- binary inspection
- high-speed artifact extraction
- future static analysis engines

Rust becomes the "engine."

Go becomes the "platform."

---

# Why Not Everything In Rust?

Rust certainly could build the entire system.

However,

our goal is also team productivity.

Go is easier for new contributors,

especially in a hackathon.

Using both languages allows each to play to its strengths.

```
Go

↓

Application Layer

↓

Rust

↓

Analysis Engine
```

The two communicate through

- FFI
- gRPC
- CLI
- shared libraries

depending on future requirements.

For the MVP,

even invoking the Rust scanner as a subprocess from Go is perfectly acceptable.

No AI.

No cloud.

No Kubernetes.

No distributed systems.

No microservices.

The MVP is intentionally simple.

```
Local Repository

↓

Discovery

↓

CBOM

↓

Risk

↓

Recommendations

↓

Dashboard
```

A hackathon rewards

clarity,

# Future Evolution

Because the architecture is modular,

future features become straightforward.

Possible additions include

- Binary reverse engineering
- Container image scanning
- Live cloud inventory
- Organization-wide policy engine
- Compliance frameworks
- CVE integration
- GitHub/GitLab plugins
- VS Code extension
- CI/CD integration
- AI-assisted report summaries

Notice something.

None of these require redesigning the architecture.

They plug into existing components.

That is exactly what extensibility means.

---

# Engineering Philosophy

Carcinus is not designed around technologies.

It is designed around responsibilities.

Technologies can change.

Architecture should not.

That is why the pipeline remains simple,

modular,

and language-independent.

---

# The Big Picture

If someone asks

> "What is Carcinus?"

You can answer:

> Carcinus is a local-first, language-agnostic cryptographic observability platform. It discovers cryptographic assets across software systems, normalizes them into a common intermediate representation, builds a Cryptographic Bill of Materials (CBOM), evaluates quantum migration risk, and generates actionable recommendations to help organizations prepare for the transition to Post-Quantum Cryptography.

That single sentence summarizes the entire architecture.

---

# Things To Remember

• Carcinus is a pipeline, not a single scanner.

• Discovery finds cryptographic evidence.

• Normalization creates a common IR.

• The CBOM is the organization's cryptographic inventory.

• The Risk Engine transforms inventory into intelligence.

• The Recommendation Engine transforms intelligence into actions.

• Reports and dashboards present information for different audiences.

• Every module has one responsibility.

• The architecture is designed for extensibility from day one.

## Architect's Reflection

I think this is where the handbook stops being "notes for SIH" and starts resembling an **internal architecture document** that a real engineering team could use.

One thing I'd add in a future section—which I think would be especially valuable for you—is a **"Why" document** for every architectural decision. For example:

- Why Tree-sitter instead of regex?
- Why an IR instead of direct analysis?
- Why a CBOM instead of scanning on demand?
- Why Go + Rust instead of one language?
- Why rule-based analysis before AI?
- Why local-first instead of SaaS?

Those are the kinds of questions judges love asking, because they reveal whether the team actually designed the system or just assembled technologies. Given your systems background, having well-reasoned answers to those tradeoffs would be a major strength during judging.
