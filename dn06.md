# Design Note 06

# The Cryptographic Bill of Materials (CBOM)

> "A scanner finds things once.
>
> A Bill of Materials becomes the source of truth."

---

# A Simple Question

Imagine you own a factory.

Someone asks,

> "How many motors are inside your machines?"

You don't walk around counting them.

Instead, you open a document.

That document already exists.

It tells you

- every component
- every supplier
- every version
- every dependency

Manufacturing has used these documents for decades.

They are called

**Bills of Materials (BOMs).**

---

# The Original BOM

A manufacturing BOM might look like this.

```
Laptop

├── Motherboard
├── CPU
├── RAM
├── SSD
├── Battery
├── Display
└── Keyboard
```

Nothing mysterious.

It's simply an inventory.

It answers

> "What is this product made of?"

---

# Software Has BOMs Too

Modern software is built from hundreds or even thousands of dependencies.

Consider a simple web application.

```
Application

├── Spring Boot
├── OpenSSL
├── Jackson
├── PostgreSQL Driver
├── Log4j
└── JWT Library
```

Keeping track of these dependencies became important,

especially after incidents like Log4Shell.

This gave rise to the

**Software Bill of Materials (SBOM).**

---

# What Is An SBOM?

An SBOM is simply

> a structured inventory of software components.

It usually records things like

- package name
- version
- supplier
- license
- dependency relationships

Notice something.

It tells us

**what software exists.**

It says almost nothing about

the cryptography inside that software.

---

# That's Where CBOM Comes In

CBOM stands for

**Cryptographic Bill of Materials.**

Instead of asking

> Which libraries does this application use?

it asks

> Which cryptographic assets exist inside this application?

This is a very different question.

---

# A Mental Model

Imagine three inventories.

```
Hardware

↓

BOM
```

```
Software

↓

SBOM
```

```
Cryptography

↓

CBOM
```

Each inventory focuses on a different aspect of the system.

---

# What Does A CBOM Contain?

A CBOM may contain information like

```
Algorithm

RSA

Key Length

2048

Library

OpenSSL

Protocol

TLS 1.2

Certificate

Expires 2027

Repository

payments-service

Owner

Security Team
```

Notice something.

This isn't source code anymore.

This is structured knowledge.

---

# Why A CBOM Is Useful

Suppose tomorrow NIST announces

> "Algorithm X should no longer be used."

Question.

Without a CBOM,

how do you find every occurrence?

You probably can't.

With a CBOM,

the query becomes almost trivial.

```
SELECT *

WHERE Algorithm = "RSA"
```

Or

```
SHOW

Certificates

expiring within 90 days
```

Or

```
Find

Repositories

still using SHA-1
```

The CBOM transforms scattered information into searchable information.

---

# The Scanner Is Not The Product

This is a very important realization.

Most beginners think

```
Repository

↓

Scanner

↓

Done
```

No.

The scanner is merely the first stage.

The real product is the continuously growing knowledge base.

```
Repositories

↓

Discovery

↓

Normalization

↓

CBOM

↓

Risk Assessment

↓

Recommendations

↓

Dashboard
```

Without the CBOM,

every scan starts from zero.

---

# Think Of Google

Google does not search the Internet every time you type something.

That would be impossibly slow.

Instead,

Google builds an index.

Searching becomes fast because the information is already organized.

A CBOM is similar.

It is an index of an organization's cryptographic landscape.

---

# A Living Inventory

One scan is never enough.

Repositories change.

Developers add libraries.

Certificates expire.

Algorithms change.

Dependencies are updated.

The CBOM must evolve with the organization.

Think of it as a database,

not a report.

---

# One Repository

Imagine scanning a repository.

```
payments-service

↓

Java Files

↓

Dockerfile

↓

application.yml

↓

Certificates

↓

Dependencies
```

Each produces discoveries.

After normalization,

the CBOM may contain

```
Asset #1

RSA-2048

Location

AuthService.java

---

Asset #2

TLS Certificate

Expires

2027

---

Asset #3

AES-256

Provider

OpenSSL

---

Asset #4

JWT Signing Key

Algorithm

RS256
```

Notice that

the repository has disappeared.

What remains is structured information.

That is exactly what inventories do.

---

# Multiple Repositories

Now imagine

500 repositories.

Instead of

500 independent scans,

Carcinus gradually builds one organization-wide CBOM.

```
Repo A

↓

Artifacts

↓

CBOM

↑

Artifacts

↑

Repo B

↑

Artifacts

↑

Repo C
```

Everything contributes to the same inventory.

This is where organization-wide visibility becomes possible.

---

# Why Not Store Raw Files?

Someone might ask,

> Why don't we simply save every source file?

Because source code is not the information we need.

Suppose two files contain

```java
Cipher.getInstance("AES")
```

and

```python
AES.new(...)
```

The source code differs.

The cryptographic information is identical.

The CBOM stores knowledge,

not syntax.

---

# CBOM Is Not A Report

Another common misunderstanding.

Reports are snapshots.

A CBOM is infrastructure.

Reports are generated

from

the CBOM.

Not the other way around.

```
CBOM

↓

Risk Report

↓

Executive Report

↓

Migration Plan

↓

Dashboard
```

The CBOM becomes the single source of truth.

Everything else consumes it.

---

# Engineering Discussion

Suppose someone asks,

> "How many repositories still use RSA?"

Without a CBOM,

you scan everything again.

Tomorrow,

someone asks,

> "Which certificates expire next month?"

You scan everything again.

The day after,

> "Which systems use TLS 1.0?"

Again,

another scan.

Eventually,

most of the work becomes repeated discovery.

A CBOM prevents this repetition.

Discover once.

Query forever.

---

# Why This Matters For Carcinus

The SIH statement repeatedly mentions

inventory.

Notice the wording.

Not

"scan"

Not

"search"

Not

"grep"

Inventory.

That word tells us something important.

The judges are not asking for

a better scanner.

They are asking for

an engineering platform

that continuously understands an organization's cryptographic landscape.

That platform revolves around the CBOM.

---

# Connecting Everything Together

Let's update our mental model.

```
Repository

↓

Discovery

↓

Normalization

↓

Cryptographic Asset

↓

CBOM

↓

Risk Engine

↓

Recommendation Engine

↓

Dashboard
```

This diagram is going to appear repeatedly throughout the rest of this handbook.

Everything downstream depends on the CBOM.

---

# Things To Remember

• A BOM inventories physical components.

• An SBOM inventories software components.

• A CBOM inventories cryptographic components.

• The scanner discovers assets.

• Normalization standardizes them.

• The CBOM stores them.

• Reports are generated from the CBOM.

• A CBOM is a living inventory, not a one-time report.

• The CBOM becomes the organization's source of truth for cryptographic visibility.
