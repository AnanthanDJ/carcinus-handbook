# Design Note 00

# Why Carcinus Exists

> "You cannot migrate what you cannot discover."

That single sentence summarizes the entire motivation behind this project.

This handbook exists to explain why.

---

## Before We Begin

This handbook intentionally avoids assuming any prior knowledge.

Some members of the team come from AI.

Some from frontend.

Some from backend.

Some have never worked with cryptography.

That is perfectly fine.

By the end of this handbook, everyone should understand:

- why this problem exists
- why governments care about it
- why existing tools only solve parts of the problem
- why Carcinus is designed the way it is

This is not a cryptography textbook.

It is not a Rust handbook.

It is not a software engineering guide.

It is the design notebook behind Carcinus.

Whenever possible, we explain *why* before explaining *how*.

---

# The Real Problem

Let's begin with a thought experiment.

Imagine tomorrow morning you arrive at Microsoft.

Your manager walks in and says,

> "Every vulnerable cryptographic algorithm must be replaced before the end of the year."

Seems straightforward.

Replace RSA.

Replace ECC.

Move to Post Quantum Cryptography.

Done.

Right?

Not even close.

The first question every engineer asks is...

> Where?

Where is RSA?

Where is ECC?

Which repositories use OpenSSL?

Which applications still depend on SHA-1?

Which certificates expire next month?

Which servers use outdated TLS configurations?

Nobody knows.

Not because engineers are careless.

Because modern software is enormous.

---

# Modern Software Is Bigger Than We Imagine

A typical enterprise is not one application.

It is hundreds.

Sometimes thousands.

Imagine an organization with:

- 850 Git repositories
- 12 programming languages
- 25 years of legacy code
- third-party libraries
- Docker containers
- Kubernetes deployments
- cloud infrastructure
- internal tooling
- vendor software

Now imagine trying to answer one seemingly simple question.

> "Where are we using RSA?"

No engineer can answer that from memory.

No spreadsheet contains that information.

No dashboard magically knows.

Some answers exist inside source code.

Some inside configuration files.

Some inside certificates.

Some inside Docker images.

Some inside binaries.

Some inside cloud infrastructure.

Some are hidden inside third-party dependencies.

Some are forgotten entirely.

Before replacing anything...

someone first has to find it.

That discovery process is exactly what this project is about.

---

# The SIH Problem Statement

The official SIH problem statement talks about

> Transitioning to Post Quantum Cryptography.

At first glance, it sounds like the project is about quantum computers.

It isn't.

Read the statement carefully.

It says,

> Discovery and inventory of cryptographic artefacts is the critical first step.

Notice what is happening.

The problem statement is not asking us to invent a new encryption algorithm.

It is not asking us to build a quantum computer.

It is not asking us to replace RSA.

Instead, it asks us to solve the problem that comes *before* all of those.

Visibility.

Until an organization understands its current cryptographic landscape, every migration plan is based on assumptions.

Engineering begins with visibility.

---

# Why This Is Becoming Urgent

If quantum computers were hundreds of years away, this problem would not exist.

But governments around the world are already preparing for migration.

Why?

Because migration itself takes years.

Large organizations cannot replace cryptography overnight.

Banks.

Governments.

Hospitals.

Telecommunication providers.

Cloud companies.

Defense organizations.

They all have software that may be decades old.

Migration involves:

discovering assets

↓

understanding dependencies

↓

evaluating risk

↓

testing replacements

↓

deployment

↓

validation

↓

maintenance

Each of those stages can take months.

Waiting until the day quantum computers become practical would already be too late.

Preparation has to begin now.

---

# What Makes This Difficult?

Suppose someone asks,

> "How many AES keys exist inside our infrastructure?"

Sounds like a database query.

It isn't.

Because the answer is scattered across many different places.

Some examples include:

Source code

Configuration files

Certificates

Infrastructure-as-Code

Container images

Binary executables

Dependency manifests

Cloud services

Hardware Security Modules

VPN configurations

Authentication servers

Each one stores cryptographic information differently.

There is no universal format.

That means discovery itself becomes an engineering challenge.

---

# Visibility Before Security

Security discussions usually begin with questions like

"Is RSA safe?"

"Should we use AES-256?"

"Is SHA-1 deprecated?"

Those are good questions.

But they assume something important.

They assume we already know where those algorithms exist.

Most organizations do not.

That changes the order of priorities.

Instead of

Security

↓

Discovery

the order becomes

Discovery

↓

Understanding

↓

Assessment

↓

Migration

↓

Security

This is the philosophy behind Carcinus.

---

# Engineering Discussion

Imagine trying to renovate an old city.

Would you begin by buying new building materials?

No.

First you need a map.

You need to know

where the roads are

which bridges exist

which buildings are unsafe

which utilities are underground

Without that map, every decision is guesswork.

Cryptographic migration is surprisingly similar.

A CBOM is that map.

Carcinus is the system that builds and analyzes it.

---

# Why This Problem Is Interesting

Many hackathon problems ask teams to build an application.

This one is different.

This problem asks us to build infrastructure.

Infrastructure is usually invisible.

People rarely notice it.

Yet almost every important system depends on it.

Operating systems.

Compilers.

Databases.

Networking.

Package managers.

Observability platforms.

Build systems.

Cryptographic visibility belongs to that category.

It is not exciting because of fancy graphics.

It is exciting because everything built afterwards depends on it.

---

# The Philosophy Behind Carcinus

Throughout this handbook, one philosophy appears repeatedly.

Visibility

↓

Understanding

↓

Assessment

↓

Recommendation

↓

Trust

Notice that AI does not appear anywhere in this pipeline.

That is intentional.

Artificial Intelligence may assist certain stages.

It does not replace understanding.

Carcinus is first and foremost an engineering platform.

Its purpose is to make cryptographic information observable.

Everything else builds upon that foundation.

---

# Things To Remember

• This project is not about building new cryptography.

• It is not about replacing RSA.

• It is not about quantum computers directly.

• It is about discovering existing cryptography.

• Discovery is the first step toward migration.

• Visibility enables assessment.

• Assessment enables migration.

• Migration enables long-term security.

Whenever you feel lost while reading future chapters, return to this sentence.

> You cannot migrate what you cannot discover.

Everything else in this handbook exists because of that idea.
