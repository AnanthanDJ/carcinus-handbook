# Design Note 11

# Reporting and Dashboard: Turning Analysis into Decisions

> "A security system succeeds not when it finds problems,
> but when people understand what those problems mean."

# Different Users Need Different Information

One mistake beginners often make is designing one report for everyone.

Real organizations don't work that way.

Different roles have different questions.

For example,

---

## Security Engineer

Wants to know

- Which repository?
- Which file?
- Which line?
- Which algorithm?
- Why was it detected?
- How confident is the detection?

They need technical detail.

---

## Team Lead

Wants to know

- Which project is most affected?
- Which team owns it?
- How much work is required?
- Which issues should we prioritize this sprint?

They need planning information.

---

## CISO / Management

Wants to know

- Overall cryptographic posture
- Number of critical findings
- Migration readiness
- Organizational risk trend

They don't need source code.

They need decisions.

---

# One Source Of Truth

Notice something.

All three reports originate from the same data.

```

↓
```

Different reports.

Different perspectives.

# Explainability

Every dashboard element should answer

```
Where did this come from?
```

Example.

Clicking

```
RSA-1024

↓

Evidence

↓

AuthService.java

↓

Line 118

↓

Detected by Rule J-014
```

Nothing should feel like magic.

Users must be able to verify findings.

# Audit Trail

Organizations need accountability.

Every scan should produce an audit record.

Example.

```
Scan Started

↓

Scanner Version

↓

Rules Used

↓

Repositories

↓

Assets Found

↓

Reports Generated

↓

Timestamp
```

This creates a reproducible history.

Weeks later,

someone should be able to answer

> "What changed?"

# Offline First

Remember the SIH constraints.

Everything operates

offline

inside an

air-gapped environment.

That means

```
Dashboard

↓

Local Browser

↓

Local Backend

↓

Local Database
```

No cloud.

No external APIs.

No internet dependency.

This is one of Carcinus's strongest differentiators.

---

# Why Local Matters

Organizations handling

- defense
- finance
- healthcare
- government
- critical infrastructure

often cannot upload repositories to cloud services.

Sometimes,

they are legally prohibited from doing so.

Carcinus respects that reality.

The entire workflow remains local.

This isn't just a feature.

For many organizations,

it's a requirement.

---

# Reports Are Outputs

Notice something subtle.

Reports are not the product.

The product is the platform.

Reports are merely one way of consuming the platform's knowledge.

Tomorrow,

someone may build

- a CLI
- a REST API
- a VS Code extension
- a Jenkins plugin

All of them consume the same CBOM.

The architecture doesn't change.

---

# Engineering Discussion

Many student projects begin by designing the UI.

Carcinus does the opposite.

We first design

- Discovery
- Normalization
- CBOM
- Risk
- Recommendations

Only then do we build the dashboard.

This is a classic systems engineering approach.

The UI becomes thin because the backend architecture is strong.

# Connecting Everything Together

The complete MVP architecture now looks like this.

```
Repositories

↓

Discovery Engine

↓

Normalization Layer

↓

Carcinus IR

↓

CBOM

↓

Risk Engine

↓

Recommendation Engine

↓

Reports

↓

Dashboard
```

Every stage has one responsibility.

Every stage can evolve independently.

That is what makes the architecture extensible.

---

# Things To Remember

• Different users need different reports.

• The CBOM remains the single source of truth.

• Technical reports prioritize detail.

• Executive reports prioritize decisions.

• Dashboards visualize knowledge, not source code.

• Every finding should be explainable.

• Audit trails provide accountability.

• Offline-first design is a major differentiator.

• Reports are consumers of the platform, not the platform itself.
