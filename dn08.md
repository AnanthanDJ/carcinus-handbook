# Design Note 08

# Normalization: Designing Carcinus's Intermediate Representation

> "Every language speaks differently.
>
> Every downstream component should not have to."

---

# The Problem

Suppose our scanner supports

- Java
- Rust
- Go
- Python

Now suppose we discover AES.

Java

```java
Cipher.getInstance("AES")
```

Rust

```rust
Aes256::new(...)
```

Python

```python
AES.new(...)
```

Go

```go
aes.NewCipher(...)
```

Four languages.

Four APIs.

Four syntaxes.

One algorithm.

Should the Risk Engine understand all four?

Absolutely not.

---

# A Thought Experiment

Imagine building the Risk Engine directly on top of language parsers.

```
Risk Engine

↓

Java Parser

↓

Rust Parser

↓

Python Parser

↓

Go Parser

↓

...

```

Now add another language.

```
C#

```

The Risk Engine must now be modified.

Add Kotlin.

Modify again.

Add Swift.

Modify again.

Eventually every new language changes every downstream component.

That is terrible architecture.

---

# One Translation Layer

Instead,

every parser translates discoveries into one common language.

```
Java

↓

IR

↑

Rust

↓

IR

↑

Python

↓

IR

↑

Go

↓

IR
```

Now every downstream component only understands

IR.

Nothing else.

---

# What Is An Intermediate Representation?

Compiler engineers use the term

Intermediate Representation (IR)

to describe an internal format that sits between

source code

and

machine code.

```
Rust

↓

AST

↓

LLVM IR

↓

Machine Code
```

LLVM doesn't care whether the original language was

Rust,

C,

Swift,

or Zig.

It only understands LLVM IR.

That is exactly the same idea we use.

---

# Carcinus IR

Instead of representing

program instructions,

our IR represents

cryptographic knowledge.

Everything eventually becomes one standardized object.

For example

```yaml
asset_type: Algorithm

name: AES

mode: GCM

key_size: 256

language: Rust

source:

    repository: payment-service

    file: crypto.rs

    line: 91

confidence: High
```

Notice something.

There is no Rust syntax anymore.

Only knowledge remains.

Java.

```java
Cipher.getInstance("AES/GCM/NoPadding")
```

Parser output

↓

```yaml
asset_type: Algorithm

```

---

Python.

```python

```

↓

IR

```yaml

```

Completely different source.

Nearly identical IR.

That is the entire point.

# Why IR Is Powerful

Suppose tomorrow we add support for

Kotlin.

How many downstream systems change?

Zero.

Only one component changes.

```
Kotlin Parser

↓

IR
```

Everything else continues working.

```
Risk Engine

Recommendation Engine

Dashboard

CBOM

Reports

Exporters
```

None of them know Kotlin exists.

---

# What Should The IR Contain?

Our IR should answer questions,

not preserve syntax.

Useful fields include

```
Asset Type

Algorithm

Key Length

Certificate

Protocol

Library

Version

Configuration

Repository

Owner

Language

Confidence

Location

Evidence
```

Every field should have a purpose.

If nothing downstream uses it,

it probably shouldn't exist.

---

# Evidence

One important design decision.

Every artifact should remember

*why* it exists.

Example

```yaml
algorithm: RSA

confidence: High

evidence:

Method Call

Cipher.getInstance()

Location

AuthService.java:118
```

Later,

if a security analyst asks

> Why did Carcinus report RSA?

we can answer immediately.

The IR should always preserve evidence.

---

# Confidence

Not every discovery is equally certain.

Suppose we see

```java
Cipher.getInstance(variable)
```

Can we determine the algorithm?

Maybe.

Maybe not.

Instead of pretending certainty,

the IR records

```yaml
confidence: Medium
```

Or

```yaml
confidence: Low
```

This becomes extremely useful later.

The dashboard can prioritize

High Confidence findings.

---

# Language Independence

Imagine looking at one IR object.

Could you tell whether it came from

Java,

Rust,

Python,

or Go?

Ideally,

no.

Language should become metadata,

not identity.

That is one sign that the normalization layer is working correctly.

---

# The CBOM Consumes IR

Remember our pipeline.

```
Discovery

↓

Normalization

↓

IR

↓

CBOM
```

Notice something.

The CBOM never sees source code.

It only receives standardized artifacts.

This makes the CBOM dramatically simpler.

# Engineering Discussion

A common mistake is treating the parser as the product.

It isn't.

The parser is simply a translator.

The real architecture begins

after translation.

This mirrors compiler design.

Most compiler optimizations happen

after

the IR exists.

Likewise,

almost every intelligent feature in Carcinus operates

after

normalization.

The IR is where the system truly begins.

---

Every future feature will connect somewhere below the IR.

That is why this layer is the heart of the architecture.

---

# Things To Remember

• Every language expresses cryptography differently.

• Downstream systems should not understand programming languages.

• The Normalization Layer converts discoveries into a common IR.

• The IR represents cryptographic knowledge, not source code.

• Evidence and confidence are first-class fields.

• The CBOM stores IR objects.

• Risk analysis consumes IR.

• Recommendations consume IR.

• Good architecture isolates language-specific logic to one layer.

• The IR is the heart of Carcinus.
