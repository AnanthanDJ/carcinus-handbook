# Design Note 07

# Discovery: How Do We Actually Find Cryptographic Assets?

> "Every engineering system begins with observation.
>
> Before we can analyze cryptography, we must first discover where it exists."

---

# The Problem

Imagine someone gives you a repository.

```
payments-service
```

Inside it are

```
12,847 files

Java

Python

Go

Docker

YAML

JSON

Markdown

Tests

Images

Videos

Documentation

Configuration

Certificates
```

Question.

How much of this actually matters?

Surprisingly...

almost none of it.

Our goal is not

> Understand the repository.

Our goal is

> Find cryptographic assets.

Those are very different problems.

---

# Thinking Like A Metal Detector

Imagine walking across a beach.

You don't inspect every grain of sand.

Instead,

you carry a metal detector.

The detector ignores

- sand
- shells
- rocks
- water

and reacts only when it detects metal.

Carcinus should behave the same way.

Ignore almost everything.

React only to cryptographic evidence.

---

# The Discovery Pipeline

Every repository enters the same pipeline.

```
Repository

↓

File Discovery

↓

Language Detection

↓

Artifact Extraction

↓

Normalization

↓

CBOM
```

Each stage has one responsibility.

Nothing more.

---

# Step 1

## File Discovery

Before reading files,

we need to know they exist.

The simplest job of the Discovery Engine is

```
Repository

↓

List every file
```

Immediately,

many files can be ignored.

Examples include

```
README.md

logo.png

video.mp4

presentation.pptx

notes.txt
```

They rarely contain cryptographic assets.

Instead,

we focus on

```
.java

.rs

.py

.go

.c

.cpp

.yml

.yaml

.conf

.pem

.crt

.key

Dockerfile
```

Already,

the search space becomes much smaller.

---

# Step 2

## Language Detection

Once a file is selected,

we identify what kind of file it is.

Examples

```
AuthService.java

↓

Java
```

```
crypto.rs

↓

Rust
```

```
docker-compose.yml

↓

YAML
```

Notice something.

Language detection is not analysis.

It merely decides

which parser should inspect the file.

---

# Step 3

## Artifact Extraction

Now the real work begins.

Suppose we encounter

```java
Cipher.getInstance("AES/GCM/NoPadding");
```

The Java parser does **not** return

```
Method Call

Expression

Literal

String

AST Node
```

Those are compiler concepts.

Carcinus is not writing a compiler.

Instead,

the parser extracts only the information we care about.

```
Algorithm

AES

Mode

GCM

Padding

None
```

Everything else is discarded.

---

# Another Example

Rust.

```rust
use rsa::RsaPrivateKey;
```

The parser extracts

```
Algorithm

RSA

Asset Type

Private Key
```

Again,

the syntax disappears.

Only the cryptographic meaning remains.

---

# Yet Another Example

OpenSSL Configuration.

```
CipherString = DEFAULT:@SECLEVEL=1
```

Discovery extracts

```
Configuration

Security Level

Cipher Policy
```

Not

```
Text

Line Number

Whitespace

Comments
```

Only useful information survives.

---

# Why Not Just Use Regex?

This is usually the first idea people have.

```
grep "RSA"

grep "AES"

grep "SHA"
```

Wouldn't that work?

Sometimes.

But only for very simple cases.

---

Consider

```java
String algorithm = "AES";

Cipher.getInstance(algorithm);
```

Regex never sees

```
AES
```

inside the function call.

Or

```java
Cipher.getInstance(
    getCipherMode()
);
```

Now the algorithm is determined elsewhere.

Regex begins to struggle.

---

Another example.

```
RSA
```

inside a comment.

```java
// TODO remove RSA later
```

Regex reports

RSA.

There is no cryptographic asset.

Only a comment.

False positive.

---

Or

```
String rsa = "hello";
```

Again,

not cryptography.

Regex cannot distinguish context.

---

# Parsing

Instead of searching text,

modern tools parse programs.

Parsing converts source code into a structured representation.

```
Source Code

↓

Parser

↓

Tree
```

This tree describes

functions

classes

variables

method calls

imports

literals

relationships

Now we can ask much smarter questions.

---

# Tree-sitter

Carcinus does not need to write parsers from scratch.

Excellent parsers already exist.

One of the most important projects is

Tree-sitter.

Tree-sitter produces syntax trees for many programming languages.

```
Java

↓

Tree-sitter

↓

Syntax Tree
```

```
Python

↓

Tree-sitter

↓

Syntax Tree
```

```
Rust

↓

Tree-sitter

↓

Syntax Tree
```

Notice something beautiful.

Different languages.

Same concept.

---

# But Tree-sitter Isn't Enough

Tree-sitter understands syntax.

It does **not** understand cryptography.

Suppose Tree-sitter finds

```
Function Call
```

It cannot tell you

> This is AES-256.

That knowledge belongs to us.

Our rules interpret the syntax.

Tree-sitter provides structure.

Carcinus provides meaning.

---

# The Rule Engine

Imagine a small rule.

```
Java

Method Call

Cipher.getInstance()

↓

Extract Cipher Specification
```

Another rule.

```
Rust

Import

rsa::RsaPrivateKey

↓

RSA Private Key
```

Another.

```
Python

Import

cryptography.hazmat

↓

Cryptography Library
```

Each language contributes rules.

Every rule produces the same thing.

Artifacts.

---

# Separation of Responsibilities

This is extremely important.

```
Tree-sitter

↓

"What is this syntax?"
```

Carcinus Rules

↓

"What does this syntax mean?"
```

Never mix the two.

That separation makes the system extensible.

---

# Why ripgrep Still Matters

Earlier,

we said regex is insufficient.

That doesn't mean regex is useless.

Imagine scanning

2 million files.

Running a parser on every file would be expensive.

Instead,

we can use

ripgrep

as a **prefilter**.

Example.

```
Repository

↓

ripgrep

↓

Files containing

AES

RSA

Cipher

Signature

TLS

↓

Tree-sitter

↓

Rules

↓

Artifacts
```

Most files never reach the parser.

Performance improves dramatically.

Think of ripgrep as the receptionist,

not the investigator.

# Discovery Is Progressive

Notice something.

We don't immediately perform

risk analysis.

We don't calculate

Mosca scores.

We don't recommend PQC.

Discovery has one responsibility.

```
Find evidence.
```

Everything else happens later.

# Engineering Discussion

Imagine mixing everything together.

```
Parser

↓

Risk

↓

Dashboard

↓

Recommendations

↓

Database
```

Now every change affects every component.

Instead,

Carcinus follows a pipeline.

```
Discovery

↓

Normalization

↓

CBOM

↓

Risk

↓

Recommendations
```

Each stage becomes independently testable.

That is much easier to maintain.

---

# Connecting This To Sonar

One reason tools like Sonar can support many languages is because they separate

language parsing

from

analysis.

Carcinus follows a similar philosophy,

but specializes entirely in cryptographic assets.

Instead of producing

code smells,

security hotspots,

or bugs,

our pipeline produces

normalized cryptographic artifacts.

The architectural principle is similar.

The domain is different.

---

# Things To Remember

• The goal is not understanding the whole repository.

• The goal is discovering cryptographic assets.

• Discovery begins with file selection.

• Language detection chooses the correct parser.

• Parsers understand syntax.

• Carcinus rules understand cryptography.

• Tree-sitter provides structure, not semantic meaning.

• ripgrep acts as a fast prefilter.

• Every discovery becomes a normalized artifact.

• Good architecture separates discovery from analysis.
