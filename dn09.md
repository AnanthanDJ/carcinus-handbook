# Design Note 09

# The Risk Engine: Turning Inventory into Intelligence

> "Finding cryptographic assets is valuable.
>
> Understanding which ones matter is invaluable."

---

# The CBOM Is Passive

At the end of Design Note 08, we have a CBOM.

Imagine it contains

```
Repository A

RSA-2048

TLS 1.2

OpenSSL 1.1

Certificate

Expires 2027

------------------

Repository B

AES-256

SHA-256

TLS 1.3

------------------

Repository C

SHA-1

RSA-1024

TLS 1.0
```

This is useful.

But only partially.

The CBOM answers

> "What exists?"

It does **not** answer

> "What should I fix first?"

---

# Engineers Don't Want Inventories

Imagine showing a CISO (Chief Information Security Officer)

a spreadsheet containing

```
17,000 cryptographic assets.
```

What is their first question?

Not

> "Interesting."

Instead they immediately ask

> "Which ones should I worry about?"

That is exactly what the Risk Engine exists to answer.

---

# Risk Is Context

Consider two systems.

System A

```
RSA-2048

Internal Development Server

Contains Test Data
```

System B

```
RSA-2048

Public Banking Portal

Processes Financial Transactions
```

Same algorithm.

Different risk.

Why?

Because cryptography never exists in isolation.

Context matters.

---

# Risk Is Not Binary

Beginners often think

```
Safe

Unsafe
```

Real engineering is rarely that simple.

Instead,

risk usually exists on a spectrum.

For example

```
Low

↓

Medium

↓

High

↓

Critical
```

This gives organizations a practical way to prioritize work.

# Rule-Based Analysis

For the MVP,

the Risk Engine does not need AI.

Simple rules already provide enormous value.

Example.

```
IF

Key Size < 2048

↓

Increase Risk
```

Another.

```
IF

SHA-1

↓

High Risk
```

Another.

```
IF

Certificate Expiring

↓

Medium Risk
```

These rules are

transparent,

explainable,

and deterministic.

---

# Explainability

Every finding must answer

three questions.

---

## What?

```
RSA-1024 detected.
```

---

## Why?

```
1024-bit RSA no longer provides an adequate security margin for modern deployments.
```

---

## What Should I Do?

```
Plan migration to a post-quantum hybrid approach or, at minimum, upgrade to stronger currently accepted configurations while preparing for PQC.
```

A warning without an explanation is frustrating.

A warning with evidence becomes actionable.

# Confidence

Earlier,

the Discovery Engine assigned confidence.

Example.

```
Confidence

High
```

```

```

```

```

# The First Version

The MVP Risk Engine can be surprisingly simple.

Pipeline.

```
IR

↓

Apply Rules

↓

Generate Findings

↓

Assign Severity

↓

Generate Report
```

Nothing more.

No machine learning.

No neural networks.

No LLMs.

Good engineering often begins with deterministic systems.

# Future Expansion

Because the Risk Engine consumes IR,

future improvements become straightforward.

Examples include

- organization-specific security policies

- compliance frameworks

- CVE integration

- cryptographic deprecation timelines

- automated migration prioritization

- AI-assisted explanations

Notice something.

None of these require changing the Discovery Engine.

That is the advantage of our architecture.

---

# Why AI Doesn't Belong Here (Yet)

Many hackathon teams immediately add AI.

But ask yourself.

Should an LLM decide whether

RSA-1024

is weaker than

RSA-4096?

Of course not.

That knowledge is objective.

Rule-based systems are

faster,

cheaper,

deterministic,

and explainable.

AI becomes useful only after the facts have already been established,

for example,

to summarize reports for executives.

Not to determine cryptographic truth.

---

# Engineering Discussion

Imagine trying to build recommendations directly from source code.

Every recommendation engine would need to understand

Java,

Rust,

Python,

Go,

C,

and every future language.

Instead,

all language complexity disappears before reaching the Risk Engine.

This keeps the architecture modular.

Discovery finds.

Normalization translates.

Risk evaluates.

Each stage performs one job well.

---

# Things To Remember

• A CBOM is an inventory, not a decision system.

• The Risk Engine converts inventory into actionable intelligence.

• Risk depends on context, not just algorithms.

• Rule-based analysis is sufficient for the MVP.

• Every finding should answer What, Why, and What Next.

• Confidence is as important as severity.

• Explainability builds trust.

• The Risk Engine consumes IR, not source code.

• Modular architecture enables future expansion without redesign.
